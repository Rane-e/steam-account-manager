# Git Branch Convention

## 1. Постоянные ветки

| Ветка       | Назначение                                                                       | Правило мержа                         |
| ----------- | -------------------------------------------------------------------------------- | ------------------------------------- |
| **main**    | Только продакшен‑код. Каждая сборка отсюда уже задеплоена (или готова к деплою). | Merge → CI/CD выпуск + тег v*X.Y.Z*   |
| **develop** | Интеграционная ветка. Все фичи и фиксы проходят через неё.                       | Merge‑request с ревью + CI unit + E2E |

>  **Больше постоянных веток не заводим** — нам их хватит!

---

## 2. Короткоживущие ветки

### 2.1 Feature

```
feature/<scope>-<slug>
# Примеры
feature/auth-jwt-backend
feature/products-table-ui
```

_Scope_ (optional): `backend`, `frontend`, `both`.
_Slug_: коротко по‑английски, через `-`.

### 2.2 Fix

```
fix/<issue>-<slug>
# Пример
fix/1234-null-pointer
```

### 2.3 Hotfix (прямо от main)

```
hotfix/<slug>
# Пример
hotfix/login-crash-prod
```

Все ветки удаляем после мержа (`--delete`).

---

## 3. Как чинить падения

| Сломалось       | Действие                                                                                  |
| --------------- | ----------------------------------------------------------------------------------------- |
| **develop**     | `fix/*` от текущего `develop` → MR → `develop`. Или `git revert <bad>` + push.            |
| **main (prod)** | `hotfix/*` от `main` → MR → `main` (urgent) → тег/деплой. Затем `git merge main→develop`. |

Откат: redeploy предыдущего тега.

---

## 4. Правила именования тегов

- При необходимости семантических релизов используем `vMAJOR.MINOR.PATCH`.
